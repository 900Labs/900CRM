# 900CRM Architecture

The product source of truth is the new 900CRM build spec: offline-first CRM
core, Tauri desktop shell, SQLite local storage, and an optional future MCP
integration layer. Sprint scopes still gate implementation. When the broad spec
requests features outside an active sprint, the sprint wins.

## Current Sprint: foundation-realignment

This sprint realigns the foundation only. It does not add new product UI,
implement an MCP server, add a built-in AI agent, add sync server behavior, or
expose raw SQL tools.

Known broad-spec conflicts deferred by this sprint:

- The broad spec includes a future `packages/ui`; this sprint only creates
  `apps/desktop`, `crates/crm-core`, `crates/crm-mcp`, and `crates/crm-sdk`.
- The broad spec describes a full MCP server package; this sprint creates only
  a compiling placeholder crate.
- The broad spec describes SDK and advanced MCP tool/resource/prompt surfaces;
  this sprint keeps them as placeholders.
- The broad spec includes future sync behavior; this sprint keeps sync local as
  a changelog/status foundation only.

## Runtime Boundaries

```text
Svelte UI
  -> Tauri command
  -> crm-core service
  -> crm-core storage repository
  -> SQLite
```

The desktop app must not own business rules or direct storage writes. Tauri
commands are IPC adapters: deserialize inputs, lock `CrmCore`, call one service
method, and serialize the result.

`crm-core` must not depend on Tauri. It owns:

- Domain/service namespaces.
- Existing CRM validation and orchestration.
- SQLite connection setup and repositories.
- Audit logging and proposed-action foundations.
- Sync changelog foundations, without server replication behavior.
- Import/export helpers behind service methods.

Future MCP and SDK crates must call `crm-core` services. They must not access
SQLite directly.

## Desktop Launch Path

Use the root workspace scripts:

```sh
npm run dev
npm run check
npm run tauri -- dev
```

The Tauri crate remains at `apps/desktop/src-tauri`. The frontend lives at
`apps/desktop/src`. A tracked `apps/desktop/build/.gitkeep` exists only so
Tauri config validation can compile from a fresh checkout; real release assets
are generated by `npm run build`.

## Rust Workspace

The root `Cargo.toml` is the workspace manifest. Acceptance for the core
boundary is:

```sh
cargo check -p crm-core
cargo check --workspace
```

`crm-core` is the only crate that owns SQLite repositories. SQL belongs under
`crates/crm-core/src/storage/`.

## Data Model

The schema direction is documented in [docs/DATA_MODEL.md](docs/DATA_MODEL.md).
The current migration is intentionally non-destructive:

- Existing v1 desktop tables remain compatible with the current UI.
- v2 creates `organizations`, `audit_log`, `external_clients`,
  `external_client_permissions`, `proposed_actions`, and `tag_links`.
- v2 adds target columns to existing `contacts`, `notes`, `tags`, and
  `sync_changelog` tables where possible.

The next migration should normalize contacts and organizations after UI and
import flows are ready for the new model.

## Transitional Debt

Known remaining foundation debt is tracked in

## MCP Readiness

MCP is optional and separate. The core app contains no built-in AI agent and no
MCP server implementation. The readiness contract is documented in
[docs/MCP_READINESS.md](docs/MCP_READINESS.md).

Core principles:

- Disabled by default.
- No direct SQL access.
- No raw SQL, shell, file, or terminal tools.
- Read-only and draft/proposed-action modes first.
- All external-client activity must be permissioned and auditable.

## Privacy

900CRM is offline-first and local-first. Privacy commitments and current
implementation boundaries are documented in [docs/PRIVACY.md](docs/PRIVACY.md).
